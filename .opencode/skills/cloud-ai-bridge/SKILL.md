# Cloud AI Bridge (LocalAssitent)

Роутинг информации к мощному облачному ИИ (DeepSeek Chat / chat.qwen.ai) через
автоматизированный браузер. Локальный ассистент собирает контекст проекта, отправляет
его облачному ИИ и сохраняет ответ — без ручного копирования.

**⚠️ Критически важно: облачные ИИ режут/искажают большие ответы!**
Всё, что вернул облачный ИИ, ОБЯЗАТЕЛЬНО проверяется на полноту перед применением
(см. раздел «Контракт полноты» и «Верификация»).

## Когда использовать

- Сложный рефакторинг / перенос кода между проектами (как блоки F,G в HeatLossRevit2)
- Анализ большого проекта целиком (после `merge_docs`)
- Генерация нового модуля/сервиса по образцу существующего
- Мозговой штурм архитектуры перед реализацией
- Все случаи, когда локальному ассистенту не хватает контекста или качества

## Когда НЕ использовать

- Мелкие точечные правки (1-3 файла) — локальный ассистент справится сам
- Задачи, где ответ ИИ обрезается/портится из-за размера (лучше чанкинг)
- Когда нужен мгновенный итеративный цикл — локальная сборка+тесты быстрее

## Рабочий процесс (последовательность шагов)

1. **ПОДГОТОВЬ контекст** — сведи файлы проекта в один TXT:
   ```bash
   python tools/merge_docs.py <dir> --ext .cs .py .xaml --output context.txt
   ```
   Убедись, что файл < ~1 МБ (облачные ИИ имеют лимиты ввода).

2. **СОБЕРИ ТЗ** (по шаблону `docs/task-template.md`):
   - Инвентарь вместо полного кода (путь | строки | namespace | зависимости)
   - Формат ответа задан заранее (таблицы, скрипты, `### SUMMARY`)
   - Требование полноты: `// END_OF_FILE` + сводка строк
   - Чанкинг: если задача большая — разбей на подзадачи по 10-15 файлов

3. **ЗАПУСТИ роутинг** (браузер + облачный ИИ):
   ```bash
   python scripts/qwen_task.py --file task.md --prompt "..."
   # или
   python pipeline.py            # DeepSeek Chat
   python main.py --scenario merge --output context.txt
   ```
   LocalAssitent сам: откроет браузер → загрузит файл → отправит промпт →
   дождётся «думания» → скопирует ответ → сохранит в `.md`.

4. **ПРОВЕРЬ ответ на полноту** (обязательно!):
   - Файлы не обрезаны: сверь количество строк с оригиналом
   - Везде есть маркер `// END of FILE`
   - Ответ содержит все запрошенные секции (по `### SUMMARY`)
   - Нет пустых/полупустых файлов и «заглушек» («...`)

5. **ПРИМЕНИ ответ** — НЕ копируй вручную! Сгенерируй/примени через скрипт:
   - Напиши `apply.ps1` который извлекает файлы из ответа и пишет на диск
   - Сохраняй в кодировке UTF-8 (BOM для .cs!) 
   - Прогони сборку и тесты ПОСЛЕ применения

6. **ВЕРИФИЦИРУЙ** — локальная сборка + тесты являются источником истины:
   - Сборка проекта → исправь все ошибки (даже если в ответе их нет)
   - Тесты — сравни с базовым состоянием (до/после)

## Контракт полноты (обязательно в каждом ТЗ)

В конце ответа облачный ИИ ДОЛЖен выдать:

```markdown
### SUMMARY
total_files: N
файл1.ext: 1234 строк | END OK
файл2.ext: 567 строк | END OK
```

И каждый файл в ответе заканчивается строкой `// END OF FILE` (маркер).
**Правило:** нет маркера `END OK` — файл не считается принятым; запись не засчитывается.

## Чанкинг (при большом объёме)

- Разбивай задачу на подзадачи размером ~10-15 файлов
- Каждая подзадача — отдельное ТЗ и отдельный запуск
- Общий объём ответного вывода держи в пределах лимита вывода облачного ИИ
  (обычно десятки КБ — см полный лимиты)

## Анти-паттерны (что НЕ делать)

- ❌ Просить вставить полные копии всех файлов в ответ — обрезается почти всегда
- ❌ Применять ответ без проверки полноты
- ❌ Молча считать ответ верным — облачный ИИ «додумывает» уместные правки
- ❌ Смешивать несколько несвязанных задач в одном запросе

## Интеграция с Revit-проектами

Типичный сценарий — перенос сервисов между проектами (HeatLossRevit2 → RevitServices).
Инструментарий из `revit-skills` актуальна: merge_docs + облачное ТЗ + apply-скрипты.
Помни: имена namespace переименовываются в  файлах — облачный ИИ часто ошибается в
этом, проверяй через сборку.
